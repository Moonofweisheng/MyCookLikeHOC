## Context

当前饭搭子添加/编辑表单位于 `src/pages/dish-duty/index.vue`，昵称输入框设置了原生 `maxlength=6`。Pinia store 已在保存动作中统一执行 `trim`、空值、重复昵称和 Unicode 字符数量校验，成员数据保存在现有本地持久化结构中。本次设计只调整输入阶段与既有保存校验的衔接。

## Goals / Non-Goals

**Goals:**

- 让 iOS 中文拼音输入法能够完成组合文本和候选字确认。
- 保持添加与编辑饭搭子最多 6 个 Unicode 字符的最终业务规则。
- 保证 H5 与微信小程序保存结果和错误提示行为一致。
- 不改变成员身份、历史快照、本地存储格式或弹层交互。

**Non-Goals:**

- 不引入输入法专用依赖或平台分支。
- 不实现实时字数截断、拼音转换或自定义输入组件。
- 不修改后端接口、Supabase 数据或既有历史成员。

## Decisions

1. **由保存校验承担长度限制，移除输入框即时 `maxlength`。**
   原生 `maxlength` 在 iOS 组合输入阶段无法区分拼音 marked text 与已确认字符，导致提前截断。移除它可以让系统输入法完成组合；保留 store 的 Unicode 字符校验可继续阻止超长昵称。相比监听 `compositionstart/compositionend`，该方案不依赖仅浏览器可用事件，兼容 uni-app 多端。

2. **复用现有 `validateNickname`，不新增状态或数据字段。**
   保存入口已经集中调用 `addMember`/`updateMember` 并反馈错误。长度计算以 `[...normalized].length` 为准，能够在候选字确认后处理中文、emoji 等 Unicode 字符，避免页面和 store 出现两套规则。

3. **增加基于最终 Unicode 字符数的实时超长提示。**
   页面继续提示“最多 6 个字”；当已确认内容超过限制时，在输入框下方显示长度修正提示。提示只提供反馈，不参与截断，也不阻断输入法组合文本；长度恢复合法后提示消失。

## Risks / Trade-offs

- [输入阶段可暂时超过 6 个字符] → 用户可能看到超长草稿，但确认保存时会收到现有“昵称最多 6 个字”提示；这是完成 iOS 拼音输入所必需的取舍。
- [不同端原生 input 行为存在差异] → 不依赖平台专属 API，以最终保存校验作为跨端一致性边界，并通过 H5/微信小程序人工验收确认。
- [缺少真实 iOS 自动化环境] → 使用静态检查、现有 UI smoke 流程，并在交付说明中明确需要真机回归拼音组合输入。

## Migration Plan

无需数据迁移或部署脚本。发布前修改页面输入属性并运行类型检查、lint、H5 构建及相关 UI/饭搭子验证；如发现回归，可仅恢复输入框属性变更，既有本地数据无需回滚。
