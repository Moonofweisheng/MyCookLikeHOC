## Context

当前应用只有首页、分类、搜索、菜谱详情和关于页，底部导航为首页与关于；应用没有正式登录、家庭空间或成员数据模型。Pinia 已通过全局持久化插件写入 `uni` 本地存储，现有视觉体系以 `src/App.vue` 中的粗描边、硬阴影和暖色插画 token 为基础。静态资源仅包含品牌 Logo 与 Tabbar SVG，没有现成角色或动效资源，也没有 Lottie、Rive 或通用动画运行库。

本变更同时影响首页入口、新页面、成员与饭局状态、规则计算、可恢复动效、静态资源和跨端验证，因此需要先明确数据边界、资源生产方式与中断恢复策略。需求行为见 `specs/dish-duty-draw/spec.md`。

## Goals / Non-Goals

**Goals:**

- 用统一的饭搭子成员库＋每次饭局快照同时支持家庭固定成员与临时聚餐；用户通过删除不再需要的成员完成清理。
- 允许同一自然日显式创建多顿独立饭局，完成一局后可继续“再开一局”，同时保留全部历史和公平统计。
- 将抽签选择逻辑与揭晓动画彻底分离，使结果可测试、可解释并能在中断后恢复。
- 为最近饭局提供可控删除：无论饭局是否完成，均可在历史卡片中发起二次确认后删除；删除只移除目标饭局记录，不影响成员库、其他饭局或长期完成统计。
- 通过受控的 Lottie 播放适配层提供加速、急停、自动清场和结果爆发节奏，且可在 H5 与微信小程序降级运行。
- 建立可维护的模块化 SVG 资源约定，使角色可复用、可替换且不与昵称和业务状态耦合。
- 保持第一版完全本地可用，不增加网络加载、授权或隐私权限。

**Non-Goals:**

- 不实现登录、家庭邀请、跨设备同步、多人确认或服务端不可篡改记录。
- 不支持真人照片、微信头像、相册选择、图片上传或 AI 在线生成头像。
- 不实现通用家务排班、积分惩罚、排行榜或公开社交能力。
- 不使用真实物理引擎、3D、整段视频、GIF、序列帧或 Rive；Lottie 仅用于本变更定义的自动揭晓特效。
- 不承诺本地设备操作者无法修改或清除历史。

## Decisions

### 1. 使用统一饭搭子成员库与饭局快照的两层数据模型

新增独立 Pinia store，并沿用现有持久化插件。状态分为：

- `members`：饭搭子成员，包含稳定 `id`、昵称、角色键、主题色、创建时间、归档时间；用户界面将设置归档时间的行为称为“删除”，并允许恢复。彻底删除仅对已归档成员开放：从 `members` 中永久移除成员档案，不修改 `meals` 中已经保存的参与者快照；如果当前仍有可编辑 `draft`，同步移除其对应 `memberId` 参与者，避免草稿引用不存在的成员。
- `meals`：每次饭局，包含独立 `id`、本地日期键、参与者快照、规则模式、候选集、既定结果、换签记录、揭晓阶段和完成状态；`dateKey` 用于分组和统计，不作为唯一键，同一天可有多条记录。
- `draft`：尚未开始抽签的当前饭局选择，仅用于编辑成员状态；开始抽签后写成不可隐式变化的饭局快照。

饭局参与者快照保存成员当时的昵称、角色、主题色及 `memberId`；新添加的饭搭子先写入成员库，再加入当前饭局草稿，因此不需要“保存为常用”转换。历史统计只计算已经完成且具有 `memberId` 的记录；同一天早先完成的多顿饭分别计数，当前未完成饭局不计数。历史数据中可能存在旧版本的临时参与者快照，继续按快照展示，不强制回填成员库，也不影响新饭局统一使用饭搭子成员。

当前饭局不是“今天唯一一条记录”，而是按创建时间选择的最新可继续记录：存在未完成饭局时恢复最新未完成饭局；当天最新一局已完成时展示完成结果并允许显式新建草稿。创建下一局时保留上一局，只清理或替换当前草稿，不按 `dateKey` 删除已有 `meals`。

选择该模型而不是只保存成员当前状态，是因为历史必须抵抗改名、换角色、删除、彻底删除和恢复；选择本地 Pinia 而不是 Supabase，是为了保持第一版无登录、无网络与低隐私成本。

### 2. 首页入口与独立页面，不扩展 Tabbar

首页在搜索区域之后增加一张紧凑的状态卡，点击进入独立饭后分工页。入口从 store 派生四种状态：无成员、待组局、已揭晓、已完成；同一天多局时以最新一局为准，已完成状态进入后同时提供“再开一局”。饭后分工页使用普通页面布局并提供返回能力，不加入底部 Tabbar。

页面底部弹框采用“遮罩关闭、内容阻止冒泡”的事件边界：遮罩点击关闭当前弹框，弹框内容面板显式阻止点击事件继续冒泡。这样不依赖微信小程序对 Vue `click.self` 修饰符的兼容实现，输入框、角色选择、按钮和说明文本在微信端点击时都不会误关闭弹框。

成员相关界面只使用“饭搭子”这一用户概念：首次为空时引导添加至少两位；组局中继续使用同一“添加饭搭子”表单，保存后立即进入统一成员库并加入当前饭局。页面不展示“常用饭搭子”“临时加入”“仅本次有效”或“保存为常用饭搭子”，一次性聚餐通过饭后删除成员完成清理；本轮不参与则使用“休息/不在场”状态表达，不删除成员。

这是对现有信息架构影响最小的方案。若未来扩展为多个家庭协作能力，再单独评估“我的/家庭”一级导航，本变更不提前引入该结构。

### 3. 抽取规则统一为本轮全员等概率

规则模块只输入本轮饭局参与者快照和随机源，输出：

- `mode`：新饭局固定为 `equal-random`；历史数据中的旧模式字段仅为向后兼容保留；
- 实际候选 `participantIds`；
- 获选 `participantId`；
- 用户可见的等概率解释。

所有状态为“参与抽取”的饭搭子都进入候选集，无论其何时添加，也无论过去参与或完成过多少次。每人的单次获选概率固定为 `1 / 本轮候选人数`。随机数只在创建结果时消费一次，测试通过注入确定性随机源覆盖候选边界，不在动画阶段重新计算。

这一选择让规则最易理解：长期公平来自等概率重复试验的期望值，而不是产品根据历史记录主动干预某一顿饭的概率。历史完成记录只用于展示和回顾，不参与新饭局的候选或概率计算。

### 4. 先持久化结果，再进入动画状态机

抽签流程采用显式阶段：

```text
editing → committing → shuffling → sealed → revealing → revealed → completed
                                ↘ skip ───────────↗
```

用户开始抽签时，先校验候选、计算结果并同步写入本地存储；只有写入成功才进入 `shuffling`。页面根据已保存阶段恢复：

- `committing` 未成功时回到可重试编辑态；
- `shuffling` 或 `sealed` 再进入时可继续揭晓，也可直接跳过；
- `revealed` 与 `completed` 直接展示既有结果。

动效计时不作为事实来源。页面隐藏或小程序进入后台后停止装饰动画，恢复时依据持久化阶段和结果重建画面。这避免定时器暂停、组件卸载或快速重复点击导致二次抽取。

### 5. 动效采用餐盘漩涡叙事，并以分段节奏替代原地循环摇摆

动效舞台由 Vue 动态层和 Lottie 特效层组成：Vue 负责餐盘、成员贴纸、昵称、结果卡和阶段状态；Lottie 负责漩涡装饰、泡沫卷走、水花和中奖爆发。业务状态机保持 `shuffling → sealed → revealing → revealed`，但 `sealed` 不再等待用户擦拭，而是由一次性 Lottie 时间线自动进入清场揭晓：

```text
加速旋转 → 交叉换位 → 向餐盘聚拢 → 急停
                                      ↓
             轻泡沫封印 → Lottie 自动卷走泡沫
                                      ↓
                         短暂停顿 → 获选成员爆发揭晓
```

标准洗牌目标时长约 1.1 秒：前段快速建立旋转方向，中段至少产生一次肉眼可辨的交叉换位，末段所有角色向餐盘中心收束并急停。动效不得仅让成员停留在固定坐标执行旋转和缩放。

不同人数使用稳定轨道模板，而不是只按均匀圆周摆放：

- 2 人：使用对角或半圆双轨交叉，确保双方实际交换视觉位置；
- 3 人：使用三角轨道并在收束前轮换一个位置；
- 4 人：使用双对角或四象限环形换位；
- 5–8 人：使用内外双轨或错峰椭圆轨道，控制重叠并保持昵称可辨认。

轨迹通过每名参与者的阶段变量、CSS 自定义属性和 `transform` 关键帧表达。实现可以为人数模板配置起点、换位点和收束点，但不引入物理引擎，也不在每帧执行随机计算。动画延迟可以产生错峰感，但最终轨迹必须确定且只消费已经持久化的结果。

### 6. 泡沫采用轻量云团，Lottie 负责自动清场

视觉层不再把每个泡沫直接画成带粗黑边的独立圆球。泡沫层由 3–5 组云团轮廓和少量轻量小泡泡组成，Lottie 清场动画负责统一卷走和消散，不使用 Canvas 像素擦除或用户命中阈值。

泡沫从餐盘中心向外膨胀并覆盖结果区域，云团之间保留空隙和层级，不形成密集“石块墙”。主要操作提示位于泡沫层之外或拥有更高层级，不需要海绵或输入设备参与。

Lottie 播放器通过统一适配层接入 H5 和微信小程序，动画不可用时降级为 CSS/静态清场；结果揭晓不依赖鼠标、触摸、触控笔或海绵输入。

适配层不得把 H5 DOM 容器作为播放流程的前置条件：微信小程序的 `view` `ref` 可能没有可供播放器使用的原生容器，此时仍需创建降级控制器并启动定时完成回调，保证阶段从 `revealing` 自动进入 `revealed`。容器可用时再额外挂接原生 Lottie 播放器。

进入 `sealed` 后自动播放清场 Lottie，泡沫沿统一方向卷走；清场完成后保留约 100–160ms 停顿，再进入结果爆发，防止泡沫和中奖角色同时出现造成视觉噪声。用户不需要完成任何擦拭输入。

### 7. 揭晓先清场再建立单一视觉焦点

进入 `revealed` 时，未获选成员向舞台边缘滑出、缩到餐盘背后或降低至装饰层，获选成员从餐盘中心弹出。餐盘、水波、放射线和少量水滴在同一爆发节点响应，随后结果卡落地；不得让泡沫、海绵、提示文字和获选者同时竞争中心区域。

结算态（`revealed` / `completed`）进一步收敛为单一焦点：舞台内只保留获选角色、弱化后的餐盘和爆发装饰，不再放置“本轮刷碗官”或昵称结果章；获选昵称、规则解释和“洗完打卡 / 再开一局”等业务操作统一由舞台下方结果卡作为唯一结算信息源承载。结算态舞台由完整动画画布收紧为约 `500rpx` 的紧凑展示区，并将获选角色、餐盘与爆发装饰重新垂直居中；`shuffling`、`sealed`、`revealing` 仍保持原动画高度，避免影响轨迹和泡沫清场。结算态隐藏洗牌轨道装饰，避免水波、角色文字和结果提示叠在餐盘中心或留下大面积无意义空白。

“跳过动效”从洗牌开始后始终可用，但应降低装饰权重；在 Lottie 播放阶段保持可发现性。跳过直接停止或隐藏当前动画并展示已保存结果，不等待剩余动画，也不触发新的抽签。揭晓动效只自动播放一次，结算态不提供重播入口，避免重复装饰干扰结果焦点。

默认使用完整揭晓动效，不在饭后分工页面提供应用内动效开关。若可靠读取到系统或平台的减少动态效果偏好，则表现层可降级为约 350ms 的成员聚拢、短促 Lottie 清场与获选者淡入或缩放，仍建立单一焦点并展示完全相同的结果；读取不到系统偏好时继续使用完整动效，不得阻断功能。

### 8. 生产资源由模块化手工 SVG、Lottie 与代码图形组成

正式实现阶段由实现者直接制作并提交生产用 SVG 与 Lottie，不要求外部设计交付。首批资源固定为：

- 8 个饭搭子角色：煎蛋、番茄、饭团、小鱼、香菇、西兰花、辣椒、面包；
- 2 个餐盘状态：脏盘、干净盘；
- 1 组自动揭晓 Lottie：漩涡、泡沫卷走、水花和放射爆发；动画不内嵌昵称、成员角色或业务结果。

SVG 角色和餐盘继续使用透明画布、现有色板、粗圆角描边和平涂色；Lottie JSON 只包含可复用的特效图层，不内嵌昵称、远程图片、外部字体或抽签逻辑。动画避免复杂滤镜、噪声和大尺寸位图，以降低小程序渲染差异。

ImageGen 只可在实施前用于一次性角色概念参考，不直接作为生产资源；生产文件仍需按统一网格重绘为 SVG。这样能保证八个角色拥有一致线宽、比例、透明边界和可维护路径，同时避免生成图片风格漂移与体积失控。

本轮动效升级不要求新增 ImageGen 或位图资源。角色、脏盘和干净盘继续复用；泡沫清场、水花、放射线与小水滴改由 Lottie 表现。播放器通过统一适配层接入，若平台运行时不可用则降级为 CSS/静态清场，不阻断结果展示。

资源先制作 2 个角色、餐盘和自动清场 Lottie 的视觉技术样例，在 H5 与微信小程序中验证尺寸、透明边缘、播放器兼容和运动观感后，再扩展完整 8 角色，避免先批量生产再返工。

### 9. 重新抽取使用换签事件而非覆盖结果

饭局保留 `drawAttempts` 序列，每次包含候选集、规则、结果、创建时间，以及前一次被排除的预定义原因。当前结果指向最后一次有效尝试；完成打卡后饭局锁定。

预定义原因第一版限定为“TA 今天不在”“TA 已承担其他任务”“临时身体不适”。“今天有情况”面板使用与成员编辑弹框一致的明确关闭按钮和遮罩关闭行为，点击原因才提交换签；选择原因后只排除当前结果成员，再根据剩余候选重新计算规则；若没有剩余候选则不追加新尝试，也不覆盖原结果。

保留事件而不是直接替换结果，可以在历史中解释换签过程，也避免无限无痕重抽削弱产品可信度。

### 10. 本地日期分组允许同日多局，历史窗口使用设备日历日

饭局以设备本地时区的 `YYYY-MM-DD` 日期键分组，不使用 UTC 截断，但日期键不限制每天只能创建一局。每局以稳定饭局 ID 区分并按 `createdAt` 排序。应用跨过午夜后新建新日期的饭局，前一日未完成记录仍保留在历史中，不自动迁移为新一天结果。日期与完成记录仅用于历史分组和展示，不参与新饭局抽取。删除历史时只移除目标饭局记录，不论其阶段是否完成，成员库与其他饭局不受影响。

这是单设备离线产品最符合用户直觉的定义；跨时区同步不在本变更范围内。

### 11. 验证策略覆盖规则、持久化、跨端与视觉契约

- 为规则纯函数补充确定性测试或可执行校验，覆盖所有饭搭子等概率、随机边界、排除后重新抽取和人数不足。
- 为 store 行为覆盖改名不丢历史、删除恢复、不同阶段饭局删除、单局结果只生成一次、中断恢复、同日多局、完成后再开一局、同日多次完成计数及本地日期边界。
- 更新 `scripts/smoke-ui.ts`，检查首页入口、独立页面、主要插画类、跳过操作、空状态和结果状态的关键契约。
- UI smoke 同时检查弹框不使用微信端不稳定的 `click.self`，并为遮罩关闭与内容区阻止冒泡保留契约。
- 为动效舞台增加可执行检查，覆盖人数模板、非固定位置洗牌、Lottie 资源和降级路径、自动清场只揭晓一次以及精简模式不改变结果。
- 动效校验覆盖微信端容器引用不可用时仍能自动完成清场并展示结果，不能因缺少 H5 DOM 容器而停留在 `revealing`。
- 微信小程序 scoped WXSS 不使用通配后代选择器（例如 `.is-paused *`）；动画暂停状态显式列举动画元素，避免生成的 `*.data-v-*` 选择器被微信开发者工具拒绝编译。
- 执行 `pnpm type-check`、`pnpm lint`、`pnpm smoke:ui`、H5 构建与微信小程序构建。
- 在 390×844 的 H5 视口与微信小程序真机/开发者工具人工验证：2、3、4、8 人轨道换位，洗牌节奏，泡沫层级，Lottie 自动清场、播放器降级、快速重复点击、后台恢复、跳过动效、系统减少动态效果降级、无横向溢出和文字截断。

## Risks / Trade-offs

- [本地记录可被修改或清除，无法提供强公平保证] → 在规则与数据说明中明确“共同认可的本地工具”边界，不使用不可篡改或绝对公平措辞。
- [短期内等概率随机可能连续选中同一成员] → 在规则说明中明确每顿饭独立随机，长期平均来自重复试验的期望值，不承诺短期轮流出现。
- [自动清场缺少用户参与] → 保留跳过和清晰阶段提示，让用户可以控制节奏但不承担擦拭操作。
- [轨道关键帧在不同人数下可能拥挤或遮挡昵称] → 为 2、3、4、5–8 人分别定义模板，并以 390×844 的 2、3、4、8 人场景作为视觉门槛。
- [多个角色 SVG 增加包体与维护成本] → 首批限制为 8 个角色，复用统一色板与画布，先做 2 个样例验证，避免复杂滤镜并检查资源体积。
- [Lottie 播放器在 H5 与微信小程序存在差异] → 通过统一适配层隔离平台 API，限制动画 JSON 体积和特性集合，并保留 CSS/静态清场降级；将双端构建与人工播放验收列为完成门槛。
- [自动揭晓降低了用户参与感] → 保留跳过和清晰的阶段状态提示，让用户可以控制节奏但不必承担擦拭操作。
- [旧版本或异常本地数据可能导致 store 初始化失败] → 为持久化状态增加版本号、运行时清洗和安全默认值；无法识别的数据退回首次使用状态，而不是阻断应用首页。

## Migration Plan

1. 新增带版本号的独立持久化 store；首次上线时当前用户没有对应键，按空成员与空历史初始化，不迁移现有菜谱或搜索数据。
2. 先提交页面、状态、规则和最小 SVG 技术样例，完成双端验证后再补齐完整角色包与最终动效。
3. 上线后若需要回滚，可移除首页入口与新页面；独立本地存储键可保留供后续版本恢复，也可在明确的数据清理版本中安全忽略。回滚不影响现有菜谱数据、搜索历史或 Supabase 数据。
